# 移动测试思维（ARTEMIS 集成）

基于通过 **ARTEMIS** 验证过的设备行为来编写可执行的测试。在编写测试之前，先探索目标应用，确认其界面、跳转和交互。使用 ARTEMIS 的设备操作或 ADB 命令来调查软硬件行为，而不是凭空假设某个交互是如何工作的。

### 1. 可运行代码原则与 ARTEMIS 探索
- **在接到编写测试的任务时**，交付带有已验证交互和明确等待条件的可运行测试代码。
- 在编写任何测试代码之前，必须使用 ARTEMIS MCP 工具交互式地运行并探索目标应用。这样才能发现 UI 状态、跳转和所需交互的确切顺序。
- 分析用户的目标测试框架，以利用其原生能力并最大化测试稳定性。
- **时序与延迟管理（探索 vs. 执行）**：
  - **最终代码中的精确时序**：虽然 ARTEMIS 的 AI 探索本身就带有模型延迟，并非严格精确计时，但你必须在最终交付物中弥合这一差距。用 ARTEMIS 发现并验证交互路径，然后在你编写的测试脚本中实现精确、确定性的时序和等待条件（`sleep`、显式/隐式等待），因为本地测试执行没有 LLM 开销。
  - **探索时补偿模型延迟**：当把涉及等待时段的探索性任务交给 ARTEMIS 时（例如等待 30 秒让页面加载或计时器结束），要根据所选模型的自然步进间隔，在任务描述中调整请求的等待时长：
    - **Flash 模型**：步骤之间的平均处理间隔约为 **5 秒**。对于需要 30 秒的延迟，指示智能体等待约 **25 秒**。
    - **Pro 模型**：轮次之间的处理间隔通常约为 **30 秒**（由于多智能体规划与验证）。流水线的自然延迟通常已覆盖所需等待时间，无需添加长时间显式延迟命令。
  - **务实的时序判断**：当用户请求提到某个动作要持续特定时长（例如"停留在此界面 2 分钟"）时，要评估精确时序在功能上是否关键。通常这些时长只是大致指引，而非严格的测试约束——运用灵活性和务实工程判断来高效达成验证目标。


### 2. 掌握 ARTEMIS 闭环架构
深入理解并根据任务场景在 ARTEMIS 的两种执行模型（**ARTEMIS Flash** 和 **ARTEMIS Pro**）之间做出选择，掌握各自对应的工作流：

- **ARTEMIS Flash（快速 / 响应式模型）**：
  - **适用场景**：为简单、高度确定性、轻量的 UI 操作或直接自动化工作流而设计。默认无步数上限（历史会被压缩而非截断），因此任务长度本身不是选择 Pro 的理由；当任务需要持久计划、经验证的检查点、笔记或书面报告、ADB / 日志诊断，或多分支探索时，才选择 Pro。
  - **执行机制（响应式循环）**：不进入 LangGraph 多节点编排：没有 Planner、没有执行前安全网，也没有 Checker。`FlashRunner` 接收用户目标、最新的 UI 元素列表和实时截图，用单个 LLM 执行"观察-思考-行动"（Observe-Think-Act），并调用动作工具直到报告任务状态。它把多次点击串成一个 `click_sequence`，以便在瞬时 UI（自动淡出的控制栏、toast）消失前捕捉它们；还可以调用 `ask_explorer` 进行元素定位，用 `search_history` / `replay_steps` / `get_step_screenshot` 查找被压缩的早期步骤，以及对会话录屏使用 `video_analyzer`。历史记录与 Pro 位于同一会话 transcript ledger 中（会话相对的 `T+mm:ss` 时钟、截图折叠为视觉摘要、较旧的步骤分块为 era）。

- **ARTEMIS Pro（深度 / 多智能体图驱动的闭环模型）**：
  - **适用场景**：为长程、高度复杂、动态多分支任务；持续监控 / 轮询循环；以及需要深度系统诊断（ADB、日志、视频）、经验证的检查点或详细书面报告的任务而设计。
  - **执行机制（计划-执行-验证-总结闭环）**：
    - **Planner（规划器）**：将复杂的高层测试目标分解为一份活的 Markdown 任务计划，含里程碑和 `verify` / `assert` 检查项。后续的里程碑修改会获得咨询性审查（一条提示加原因回传给 Operator；计划绝不回滚）。
    - **Operator（执行器）**：消费计划，分析当前屏幕状态（截图加 UI 元素列表，并由 Explorer 以 `explorer_mode` 感知深度进行定位：`flash` 单次、`pro` 三轮、`ultra` 深度缩放），记录笔记，执行精确的设备交互；它还能召回压缩后的历史、分析会话录屏，并运行 ADB 命令作为 UI 操作的补充。
    - **安全网与执行事件**：单个以轮次结束的动作会经过执行前安全网审查（XML 优先、像素兜底）。多动作轮次是**快速动作连发（fast-action burst）**，不经过安全网而接连触发，这是 Operator 对抗瞬时 UI 轮次延迟的方式。当某个动作被拦截或失败时，系统会开启一个**执行事件（execution incident）**，它在 Operator 的上下文中持续存在（连续失败次数作为事实显示），直到后续某个动作成功执行；恢复由 Operator 自行决策，没有独立的修复 agent。
    - **Checker（验证器）**：只读校验器，拥有与 Operator 相同的观察工具，审查计划声明的检查点，并针对原始目标执行退出终审；`verification_level` 选择深度（`off`、`final` = 仅退出终审且为默认值、`checkpoints` = 每个检查点加退出终审、`strict` = 检查点且修复预算更大，断言失败则中止运行）。
    - **Outputter（输出器，可选）**：将整个执行轨迹综合成一份人类可读的报告，详述每个动作步骤和视觉结果。

### 3. 设备与环境约束及多设备管理
- **设备选择与多设备执行**：ARTEMIS 支持多设备执行和每设备并发。你可以通过两种模式控制设备定向：
  - **直接指定设备**：通过 `device_serial` 向 `mobile_run_task` 或 `mobile_get_device_state` 显式提供目标手机的序列号。以不同设备为目标的任务并发运行，互不阻塞。
  - **自动选择设备**：当省略 `device_serial` 或将其设为 `None` 时，ARTEMIS 会自动选择一台可用的已连接设备，或从设备池分配一台空闲设备。
- **设备选择优先尊重用户**：
  - 当检测到多个已连接的设备或模拟器时，或设备选择存在歧义时，**你必须优先询问用户**选择或确认其偏好的设备序列号，然后再启动任务。
- **使用 `adb devices` 诊断设备**：
  - 在准备任务或排查设备问题时，通过 bash 命令执行使用 `adb devices`（或 `adb devices -l`）诊断已连接的硬件、检查连接状态（`device`、`unauthorized`、`offline`），并获取设备序列号和型号。
- **ADB 与文件传输**：虽然 ARTEMIS 擅长设备自动化，但它运行在设备边界之内。要将诊断文件、日志或测试产物从移动设备提取到主机 PC 以进一步分析，你必须手动执行相应的 `adb` 命令（例如 `adb -s <serial> pull ...`）。
- **硬件前提**：运行 ARTEMIS 至少需要一台物理连接且完全授权的 Android 设备（例如 Pixel 手机），或一个正在运行的模拟器。
- **每设备互斥**：ARTEMIS 管理每设备执行互斥锁（`DeviceExecutionLock`）。一台设备一次只能执行一个任务（FIFO 队列），而不同设备可以并行执行任务。

### 4. 健壮的测试代码设计（"动态定位优先、坐标兜底"理念）
*如果你的任务涉及编写测试代码，必须遵循以下设计原则以获得最大可靠性：*
- **适配框架能力**：你必须先评估用户的测试框架支持哪些定位机制（例如资源 ID、XPath、文本匹配、OCR、图像模板匹配，或绝对/相对坐标）。
- **核心原则：动态定位优先、坐标兜底**：
  - 在框架支持的范围内，**始终优先使用动态元素定位**（使用 ID、文本、OCR 等），以确保测试代码能抵御 UI 布局漂移和分辨率变化。
  - 在动态定位失败或不可用时，使用**绝对坐标作为可靠兜底**，以保证执行成功。
- **实现弹性的定位模式**：
  - **双能力框架**：如果框架同时支持动态定位和基于坐标的定位，实现 **Try-Catch 兜底模式**：
    1. **Try（尝试）**：先用动态定位器（ID、OCR、文本）尝试与元素交互，以最大程度抵御 UI 变化。
    2. **Catch（捕获）**：如果动态尝试失败，回退到你在 ARTEMIS 探索期间验证过的精确绝对坐标。
  - **仅坐标框架**：如果框架只支持坐标，确保坐标有完整文档，并尽可能参数化或相对于屏幕边界定义，以缓解分辨率差异。
  - **仅动态框架**：如果框架不支持基于坐标的点击，则完全专注于生成高度健壮的动态定位器，充分利用 ARTEMIS 的元素描述和 XML 树分析。

### 5. 环境自诊断（`mobile_diagnose`）
- **先诊断，别猜**：每当 ARTEMIS 工具返回错误、任务无法启动或被拒绝、找不到设备，或用户报告 ARTEMIS 在 IDE 中"不工作"时，首先调用 `mobile_diagnose`。不要靠反复试错地重新运行 `mobile_run_task` 来排查，也不要在拿到报告之前就让用户手动运行 `adb` 命令。
- **如果 `mobile_diagnose` 根本不在你的工具列表中**，说明 MCP 服务器本身启动失败：检查 IDE 的 MCP 服务器日志，并在项目目录中运行 `uv run artemis doctor`（CLI 共用同一套检查）。
- **按顺序执行 `next_steps`**：报告按依赖顺序列出修复步骤（Python 运行时 → 配置 → MCP 主机 → LLM 凭据 → 设备 → 可选视频工具链）。`Run:` 行是单条、本地、非破坏性的 shell 命令（每行一条命令，不用 `&&`），你可以自行执行（用 winget / brew / apt 安装软件前先询问）。`Guidance:` 行描述只有用户才能做的事（解锁手机、在 USB 调试提示上点"允许"、插上数据线、释放端口、告诉你他们用哪个 IDE）——原样转达即可。`Docs:` 行是参考资料。
- **先让 ARTEMIS 自修复**：在请求手动 ADB 干预之前，先调用 `mobile_diagnose(attempt_fix=true)`；它会重新生成损坏的 ADB RSA 密钥，在安全时重启 ADB 服务器（没有就绪设备、没有任务占用设备），并清除崩溃运行器遗留的陈旧设备锁 / 队列票据。
- **按需进行深度检查**：`verify_credentials=true` 会实时校验已配置的 API 密钥（约 12 秒；适用于密钥存在但任务因认证 / 配额错误而失败的情况；结果在 `credentials` 中）。`probe_device=true` 执行真正的端到端检查——截图加通过 UIAutomator 获取的 UI 层级（约 20 秒；适用于设备显示已连接但观察或任务失败的情况；结果在 `device_probe` 中）。
- **模拟器**：`launch_avd="<name>"` 通过 ARTEMIS 的模拟器管理器在后台启动已安装的 Android 虚拟设备，并立即返回；启动需要 1-3 分钟，因此约 60 秒后重新运行 `mobile_diagnose`。绝不要自己在 shell 中运行 `emulator -avd`——它是前台进程，会挂住 shell。
- **忙碌设备**：`tasks: {active, queued}` 列出当前占用或等待设备的任务。设备忙碌意味着需要等待，或用 `mobile_manage_task(action="stop", trace_id=...)` 停止该任务。
- **凭据绝不经过聊天**：如果 LLM 密钥缺失，请让用户把密钥加到报告显示路径（`host.env_file`）的 `.env` 文件中，或加到 MCP 服务器的 `env` 块中，然后重启 MCP 服务器。`artemis init` 是交互式的，无法通过工具调用来驱动。
- **配置变更后重启**：设置在服务器启动时读取。编辑 `.env`、`config/artemis.jsonc` 或 MCP 客户端配置后，在 IDE 中重新加载 MCP 服务器，再调用 `mobile_diagnose`；否则它报告的是旧状态。
- **失败任务**：`logs.last_failed_task` 给出 trace id、其 `stderr_log` 和 `recent_errors`（即该 stderr 中的错误行，因此无需打开文件）；在重新运行任务前先阅读这些。再次委派任务前，重复 `mobile_diagnose` 直到 `verdict` 为 `ready` 或 `degraded`（`degraded` 表示任务可运行但有可选项未就绪：视频工具、OCR 密钥、次要凭据，或主机警告如解释器不匹配、守护进程端口被占用；向其 `[OPTIONAL]` 步骤转达给用户，不要在这些步骤上循环）。
